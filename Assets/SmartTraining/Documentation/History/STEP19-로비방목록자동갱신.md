# STEP19: 로비 방 목록 자동 갱신

## 변경 함수
- 서버 `LobbyUpdatesHub.Subscribe`: 로그인 사용자는 전체 로비 목록을 구독할 수 있습니다. 방 상세 변경은 현재 입장한 로비만 구독합니다. 기존 전용 로비 서버용 `LobbyHub`와 별도입니다.
- 서버 `LobbyRoomUpdates.CollectChanges`: 구독 중인 로비의 공개 방 요약을 비교해 변경 알림을 생성합니다. 방 생성·삭제, 접속·예약 인원, 방장, 이름·정원, 입장 잠금·진행 상태를 감지합니다.
- 서버 `LobbyRoomUpdatesService.ExecuteAsync`: 약 1초마다 변경 알림을 SignalR로 전송합니다. 변경이 없으면 전송하지 않으며 같은 구간의 여러 변경은 묶습니다.
- Unity `ApiLobbyScreen.UpdateLobbyRooms` / `RefreshLiveRooms`: 알림을 받으면 로비 목록의 사용자 수·방 개수를 다시 조회하고, 현재 입장한 로비의 방 목록도 갱신합니다. 로비 입장 전에도 로비 목록은 자동 갱신됩니다. 선택한 방이 삭제되면 선택도 해제합니다.
- Unity `ConnectLobbyRooms` / `DisposeLobbyUpdates`: 입장한 로비에 연결하고, 로비 변경·로그아웃·종료 시 연결을 정리합니다. 알림 연결 장애 시 약 3초 뒤 재시도하며 다시 연결되면 목록을 조회합니다.
- Unity `TrainingApiClient.ConnectLobbyUpdates` / `RoomHubConnection.Connect`: Authorization 헤더로 인증합니다. 토큰을 URL에 넣지 않습니다.

## 확인 방법
1. ASP.NET을 재시작하고 두 Unity 클라이언트로 같은 로비에 입장합니다.
   한 클라이언트는 로그인만 하고 로비에 입장하지 않아도 됩니다. 다른 사용자의 로비 입장·퇴장과 방 생성 시 로비 목록 행의 사용자 수·방 개수가 자동 갱신되어야 합니다.
2. 한쪽에서 방을 생성하면 다른 쪽 목록에 자동으로 나타나는지 확인합니다.
3. 방 입장·퇴장 후 접속 및 예약 인원이 자동 갱신되는지 확인합니다.
4. 방장이 이름·정원, 입장 잠금, 시작·대기 복귀를 변경할 때 다른 화면의 방 목록에도 반영되는지 확인합니다.
5. 마지막 참가자가 퇴장해 방이 삭제되면 목록에서도 사라져야 합니다.
6. 다른 로비로 이동하면 이전 로비의 변경이 반영되지 않아야 합니다.

알림 처리와 목록 조회에는 통신 시간이 필요합니다. 최신 입장 가능 여부는 서버가 입장 요청 시 다시 검사합니다. 새로고침 버튼도 사용할 수 있습니다.

## 검증 범위
서버 검증은 인증·로비 범위, 전체 공개 상태 변경 감지, 중복 알림 억제, 로비 퇴장·토큰 변경 후 구독 종료를 확인합니다. Unity 통합 검증은 익명 WebSocket 거절, 초기 목록 자동 조회, 다른 참가자의 이름·정원·잠금 변경 반영, 알림 재연결 중 Netcode 연결 유지 및 최신 상태 재조회를 확인합니다.

훈련 콘텐츠는 추가하지 않았으며 GitHub 업로드는 별도 요청 시 진행합니다.

## 로비 목록 숫자 갱신 보완
처음 구현에서는 방 목록만 다시 조회해 로비 목록 행의 방 개수·사용자 수가 남아 있었습니다. 이제 공개 로비 요약 변경도 알림에 포함하고 `RefreshLiveRooms`에서 `GetLobbies`를 먼저 실행합니다. HTTP 주소가 HTTPS로 이동하는 경우 REST 요청에서 확인한 최종 주소를 알림 연결에도 적용합니다.

추가 통합 검증은 로그인만 한 관찰자 화면에서 방 생성 후 방 개수 증가, 다른 사용자 입장·퇴장 후 사용자 수 증감을 확인합니다. 테스트 실행 주소는 `SMART_TRAINING_TEST_HTTP_URL`로 HTTP 주소를 별도로 지정할 수 있습니다.
